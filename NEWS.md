PIDE MCP NEWS -- history of user-relevant changes
=================================================

New in this PIDE MCP version
----------------------------

* Auto-inspect's possibly relevant facts depend on subgoal 1 of the goal only (its premises and conclusion, as before), now without the chained facts (`using`), which in Sledgehammer's relevance filter get a bonus and change the weights of their constants; the label says `subgoal 1 of …` when the goal has several subgoals. The `suggest_facts` tool still includes the chained facts, like Sledgehammer.
* Auto-inspect of a failed terminal step (`by m1 m2`, `by m`, `qed m`, `.`, `..`, `done` with the last `apply`) replays its methods without instrumentation and says which case occurred, shows the goal at that point (`goal_max_lines` default cap, qualified names) and computes the possibly relevant facts for it: `the first method fails` (goal before the first method), `the first method applies; the second method fails` (goal after the first method), or `both methods apply, but the proof is not finished: N subgoals left` (`the method applies, …`, `the last `apply` applies, …`; the subgoals left after the finishing step). JSON: `scenario` (`method_fails`, `second_method_fails`, `proof_not_finished`), `goal_state`, `goal_state_for`, `suggested_for`. This replaces `succeeds but does not finish the proof` for these steps. Not for `apply`/`proof m` (no finishing step), nor for a step that was probed while still running.
* Auto-inspect: `suggested facts` reads `possibly relevant facts` in `get_state` and in the log (`possibly relevant facts (for the 1 subgoal left): …`); the JSON field is still `suggested_facts`.
* Auto-inspect of a failed terminal step (`by`, `done`, `qed`, `.`, `..`) whose method succeeds but leaves goals: `` `m` succeeds but does not finish the proof: N subgoal(s) left`` (before: `succeeds`), with the suggested facts for subgoal 1 of the goal left after the method and the finishing step (`suggested facts (for the 1 subgoal left): …`), not for the goal before it. JSON: `subgoals_left`, `suggested_for`. A method that fails keeps the suggestions for the goal before it.
* Auto-inspect: the `top rules` also leave out sort membership rules: a statement `OFCLASS(…)`, the rules Axclass records for a class (`X_class_def`, `X_class.intro`, `X_class.axioms`) and the intro rules and axioms of its class locale (`class.X.intro`, `class.X_axioms.intro`). Class assumptions and class parameter definitions (instance definitions) stay.
* Qualified names: a `lift_bnf` map function, whose internal name repeats its theory (`Seq.seq.Seq.map_seq`), prints as `Seq.map_seq`; a constant hidden by `hide_const (open)` (`Limited_Sequence.map_seq`) no longer makes a constant with its base name count as shadowing.
* Timing in `get_state` says which run it belongs to: the real (un-instrumented) run of the command, or the diagnostic, the instrumented copy of the method that auto-inspect and `apply_inspect` run, which counts every rule use and is slower. A running command shows `(running for N s)`, once its diagnostic has started `(running for N s; diagnostic for slow method running for M s)`, after the diagnostic's time limit `(running for N s; diagnostic for slow method timed out at 5s)` followed by its results (`` `m`: N rule uses in the diagnostic``); a step that then finishes says `the step finished OK in N s (real run); diagnostic for slow method timed out at 5s`. JSON: `running_ms` for every running command (the real run), and in `inspection` `diagnostic_running_seconds`, `diagnostic_timed_out_at_seconds`, `real_finished_ms` (`probe_seconds`: the diagnostic's duration, as before); the trigger reads `real run over 5 s` (before: `running for 5 s`). No timing hints: the label `still_running_possibly_nonterminating` starts when the real run reaches `pide_mcp_possibly_looping_after` seconds (new option, default 30; before: 5 s, `pide_mcp_auto_inspect_after`, which now only starts the diagnostic), so `commands_running_briefly` counts the running commands under 30 s; the diagnostic's time-out no longer says `(it may loop)` or `slow:`, `slow steps (inspected)` is `inspected steps that finished OK` (kind `finished`), and the PROVISIONAL note no longer calls a running command a slow method to replace. `apply_inspect`'s time-out says that the instrumented method did not finish. The `pide-mcp` skill says that both are instrumented and slower than the real method.
* The `apply_inspect` submodule is at 3d5121c (before: c7aeb0f): an inspection after a failed proof of another lemma in the same theory no longer reports that proof's error ("Failed to finish proof" with its goals) for an unrelated method, and unfinished proofs of other theorems are not waited for (`apply_inspect_join_timeout`). The instrumentation is slower: a probe gets through fewer rule uses within its time limit.
* `find_theorems` / `find_consts` / `eval_ml` / `suggest_facts`: a query that fails with an inner syntax, lexical or type error says at which line it ran, with a hint at a wrong context (`(searched at line 120; wrong context?)`).
* `edit`: `reprocessed` names the slowest commands the edit makes Isabelle run again, by their previous time (at least 2 s, top 3): those from the edited line on in the edited theory and those of the theories importing it, e.g. `slowest_commands: line 10 (3 s), Slow_B.thy line 5 (3 s)`. Proofs that run in parallel (`by` of a lemma), which PIDE does not time, count with the time the server saw them running (remembered for runs of 1 s or more).
* `get_state`: a command that has run for less than `pide_mcp_auto_inspect_after` seconds (default 5) shows as `running` (`[running]  (running for 186 ms)`, header `1 running`) instead of `still_running_possibly_nonterminating`, which starts at 5 s, as do the hints for running commands. JSON: `commands_still_running_possibly_nonterminating` still counts all running commands; the new `commands_running_briefly` is the part under the threshold, and their `status`/`kinds` say `running`.
* Auto-inspect: a step that was probed while running and then finished OK says `slow: the step finished OK in N s; the probe stopped at its time limit` instead of `did not finish ... (it may loop)`; the `top rules` leave out infrastructure (theorems of Pure and of the theory HOL, `*.super`, `arity_*`, `classrel_*`, unnamed rules), which still count in the totals and are marked in the log; when one rule has at least half of the remaining uses (or three times the next one, and at least 10), a line `most uses: `r` ×N (of M non-infrastructure uses): consider a more direct rule for its instances` follows (`dominant_rule` in JSON).
* Tool output (goals, messages, `find_theorems`/`find_consts` results) prints a constant with its full name when its notation is a single word that hides it, e.g. `notation my_map ("map")` from an included bundle shows `Foo.my_map` instead of a `map` that looks like `List.map`. Notation with symbols or several tokens (`@`, `∀x.`, `if … then … else`, `THE x.`) is unchanged, and Isabelle already qualifies ambiguous names itself. Also qualified: a constant outside the standard library (the theories under `$ISABELLE_HOME/src`: AFP and project constants, also when they are part of the session image) printed by its plain name while another constant of the session image has the same base name (a project's own `map` printed as plain `map` while `List.map` exists); the image's constants are listed once in the background after a session start (through the `eval_ml` helper). Only the MCP's copy of the messages is rewritten (from their markup), not the prover's printing. Option `pide_mcp_qualify_names`: `notation` (default), `outside_base` (also every constant from a theory outside the base sessions), `all`, `none`.
* Automatic inspection covers every failing proof line: `apply`, `by` (with two methods, both, as `(m1, m2)`), `proof <method>`, `qed <method>`, `.` (`this`) and `..` (`standard`); a failing `done` replays the last `apply` of its proof on the goal it got, a `qed` without method replays nothing. For each failure, Sledgehammer's relevance filter also suggests facts for the failing goal (the state before the failed command; for `done`/`qed` the leftover subgoals): `suggested facts: a, b, c, d, e` in the auto-inspect block, all 20 with statements in the log file (`suggested_facts` in JSON). Follow-on failures (an earlier command of the same proof failed) are not probed; the queue holds 16 probes.
* Automatic inspection of slow or failed proof steps (HOL-based sessions): an `apply`/`by` step that is still running after `pide_mcp_auto_inspect_after` seconds (default 5), or that fails, is run again in the background by the `apply_inspect` instrumentation with every use counted (`pide_mcp_auto_inspect_timeout`, default 5 s). `get_state` shows for that command `auto-inspect (trigger): the method ..., N rule uses`, a loop warning and the top 5 rules with counts, plus the full trace (counts, then every use in order) in `.pide_mcp/apply_inspect/auto_inspect_*.txt` (`inspection` in JSON); slow steps that finished OK are listed under `slow steps (inspected)`. One probe at a time per session (queue of 8); a probe is stopped and dropped when its step is edited, removed or cancelled. The helper theory is loaded at session start. Off with `pide_mcp_auto_inspect = false`.
* `get_state`: the default `goal_max_lines` is 40 (before: 100), for goals and goals inside error messages, with a cap of 40 × 200 characters; raise it for more.
* `get_state` points to `apply_inspect` where it helps: a one-line hint while a command is `still_running_possibly_nonterminating` (whether it loops, which rules it uses), and in the failing-proof hint (what a failing method tried).
* `isabelle-proof-development` skill, traps: `thm[simplified]` normalises numerals (`1` becomes `Suc 0` for nat); name the rules (`[simplified add_0]`, `[unfolded …]`) or give the instance.
* The first `get_state` of a server run that shows a `sorry`, a failure or an open proof ends with `hint: proving? Load the isabelle-proof-development skill if you have not (shown once)`; it is never repeated.
* After `cancel` (or a time limit), a command that has not stopped yet shows `(running for N s; interrupt sent M s ago, waiting for it to stop)` in `get_state` (`interrupt_sent_seconds` in JSON) instead of plain `still running`.
* `get_session_state`: new `theory_paths` resolves session-qualified theory names to their source files (`HOL-Library.Multiset: .../src/HOL/Library/Multiset.thy`), so an agent that greps does not guess paths; `include_loaded_theories` gives the source file of base-session theories too.
* Goals inside error and warning messages (`Failed to apply proof method`, `Failed to finish proof`) are capped like goals: `goal_max_lines` in `get_state` (default 100), 40 lines in `edit`'s check, with the same size note and marker.
* `get_state` (and `edit` with `check`) collapse follow-on problems: after a failing `apply` step or goal statement, the later failing commands of the same proof (they run on the state before the failure) and the `Bad context` failures after a proof left open are counted but listed as one line per cause, `+ N follow-on problem(s) (line a-b) after the failed `apply` at line k`. A new `have`/`show` or theory command starts afresh (structured Isar steps fail independently and stay listed); a range that starts after the failure shows them in full.
* `get_state`: a goal of 30 lines or more starts with its size (`goal: N lines, M characters`), one of 200 lines or more is marked VERY LARGE (a method blew the term up); new `goal_max_lines` (default 100, also caps characters) cuts goals with `(+N more lines ...; raise goal_max_lines)`. `cancel` that finds nothing running names the commands of the range that finished in the last minute, with their status. `find_theorems`, `find_consts`, `eval_ml`, `suggest_facts` without `start_line`: the default position is the last command before the theory's `end` (before: the last non-`end` command, which behind an `end` fence gave `Unknown context`), and the last processed command while the end of the file is still running, with a note; an `Unknown context` result explains itself.
* Shorter context: the `pide-mcp` skill is 5.7k characters (before: 24.4k), with session setup, libraries, batch builds and ML files moved to the reference files `sessions.md` and `ml_files.md` next to it (read on demand); `isabelle-proof-development` is 5.0k (before: 14.3k). Parameter semantics live in the tool schemas only, and the tool schemas are 22.7k characters (before: 35.1k). The `pide-mcp` skill describes fencing off the rest of a theory with `end` while working on a proof. The "ACTION REQUIRED" note on synced edits (asking the agent to pass the sync-diff link to the user) is gone; the diff file is still written and its path still shown as `full diff: <path>`, for the PostToolUse hook.
* New tool `cancel` interrupts the running commands of a theory (`origin`, optional `start_line`/`end_line`; without lines all of the file) without unloading it, via PIDE's `cancel_exec`. The command then shows as `canceled` with `cancelled after N s`; a parallel proof (`by` of a lemma) lets the file go on, otherwise the commands after it stay unprocessed (`BLOCKED`) until the cancelled command is edited, which reprocesses it and everything after it. `edit` has `cancel_after_seconds`: a time limit for each command of the edited lines. `get_state` shows how long a running command has been running (`running for N s`, also for parallel proofs, which PIDE does not time).
* Non-blocking edit loop: the skills, the server instructions and the tool descriptions no longer recommend `edit` with `check: true` or `get_state` with `wait_settled` after an edit (both block while a slow method runs, 3-9 minutes per task in one comparison). After an edit, call `get_state` without waiting and treat commands still running after a few seconds as a hint to replace a slow method. `check` stays an opt-in (default false); the PROVISIONAL note says to call `get_state` again instead of waiting.
* Add Isabelle/ML skill file.
* New tool `apply_inspect` runs a proof method on the goal at a position without changing the file and lists the theorems it used: for a failing method, what it tried (simp rules, rules of the classical reasoner, local facts and assumptions), which `Failed to apply proof method` does not say. It warns when the simplifier, the classical reasoner or a repeated method seems to loop, naming the rules, and stops the method after `method_timeout` (default 10 s), still reporting what it used until then. `criteria` filters the theorems with `find_theorems` criteria; `to_file: true` writes the complete list with the statement of each theorem (`name: statement`) to a file in `.pide_mcp/apply_inspect` (the newest 100 are kept) and returns its path, for `grep`. It loads [ml/PIDE\_MCP\_Apply\_Inspect.thy](./ml/PIDE_MCP_Apply_Inspect.thy) on demand, which imports the `apply_inspect` command from the git submodule `deps/apply_inspect` (run `git submodule update --init` after pulling); a theorem in the list carries its `simp`/classical declarations (e.g. `rev_rev_ident [simp]`). Needs a HOL-based session.
* New tool `suggest_facts` lists the facts that Sledgehammer's relevance filter (MePo/MaSh) selects for the goal at a position, most relevant first, without running provers. It loads the helper theory [ml/PIDE\_MCP\_Suggest.thy](./ml/PIDE_MCP_Suggest.thy) into the session on demand, which registers a PIDE query operation. Needs a HOL-based session.
* New tools `find_theorems` and `find_consts` run Isabelle's searches as PIDE queries at a position of a file without modifying it (before, the agent had to insert the Isar commands into a theory). The skills and the server instructions recommend them over grepping imported sources.
* The `pide-mcp` skill has a "Before You Start" section: check that the MCP tools exist and answer, and if not, stop and report the exact failure to the user instead of silently falling back to batch builds. The other skills and the server instructions point to it.
* The server instructions (always in the agent's context) now name the `pide-mcp` and `isabelle-proof-development` skills, ask for a `get_state` check after every edit, and recommend `try0`, then `sledgehammer [timeout = 10]` (always with a short timeout) for goals that do not close. The `isabelle-proof-development` skill and the sledgehammer tool extension say the same.
* Agents that never loaded the proof tools (deferred by clients like Claude Code) kept guessing proof methods. The server instructions and the `pide-mcp` skill now ask to load `sledgehammer`, `suggest_facts`, `find_theorems`, `find_consts` and `create_scratch` up front, and the text output of `get_state` ends with a hint to run `try0` / `sledgehammer [timeout = 10]` when commands fail or have errors.
* New tool `eval_ml` evaluates ML code in the context at a position of a loaded theory, including the ML structures of imported theories (e.g. from `ML_file`), without modifying any file. It replaces inserting `tracing` calls into an ML file, which reloads the file and all its dependents.
* `get_state`: new argument `wait_settled` (with `wait_seconds`) waits until the file and the imported theories it depends on are completely processed, or the file has a failed command. The maximum of `wait_seconds` is now 3600.
* `edit`: new argument `check` also returns the status summary of the whole file (counts and first problem) after processing the edit.
* `edit` no longer rewrites lines it does not touch: before, the whole file was symbol-encoded on write, so literal Unicode symbols (e.g. `⋀`) elsewhere in the file became `\<And>` and dirtied diffs. Lines outside the edit keep their disk text byte for byte.
* `edit` reports `reprocessed`: the number of loaded theories and commands that the edit makes Isabelle process again (the file and all theories importing it, for an ML file the theories loading it) and how long processing them took before.
* `eval_ml`: ML errors carry the line within the code (`ML error (line 3)`).
* `get_state` marks results that may still change with a `*** PROVISIONAL RESULT ... ***` line (commands of the range still unprocessed/running, or the file waits for imported theories), and `edit` with `check` has a `provisional` entry likewise. After a call synchronised external edits from disk, `get_state` waits up to 5 seconds (before: 30) for the file to settle even without `wait_seconds`.
* `find_theorems`, `find_consts`, `suggest_facts`: without `start_line` the position is the end of the file (before: the theory header, where facts defined in the file are invisible); the result says so. Empty results hint at theories that are not imported. `prefix` ignores leading whitespace.
* `edit`: `old_text` is matched with symbols in Unicode form, so `\<rightarrow>` matches a stored `→`.
* `get_session_state` has a `machine` block: free and total memory and the number and total memory of all Isabelle java/poly processes of the user (all servers, not only the answering one), plus this server's own share. `start_session` refuses to start when less than `min_available_mb` (default 4096) MB are available (it states the current Isabelle total); `ignore_memory_check: true` overrides.
* `edit`: `reprocessed` is always present after a change: it also finds the theories that load an ML file while that file is being reprocessed, and says `unavailable` with a reason where it cannot tell.
* Hints in the text of `get_state`: an unqualified theory import (`Bad theory import "Box"`) points to session-qualified names (`Box.Box`); an `Interrupt` (e.g. `Interrupt_Breakdown`) is explained as a time limit or cancellation, not a logic error. `create_scratch` documents qualified imports.
* New tool `check_ml`: checks ML text (a file or given code) for syntax errors WITHOUT running it and without a session or reload (about 0.2 s): the text is compiled by the stand-alone Poly/ML compiler (`ml/check_syntax.sml`), antiquotations are replaced, only `infix` declarations are run, and the compiled code never is. It finds errors like a trailing comma in a record type; names and types are not checked (earlier declarations are not run). No false alarm in 699 of 700 files of Isabelle's own ML sources plus all ML files of the Box library (the 700th used `\<^if_unix>` conditionals, now handled). `edit` runs it before writing an `.ML` file (`check_ml`, default true) and does not write a file with a syntax error; a changed `.ML` file found by `get_state` on disk reports its syntax error in the sync note. This catches before the reload what one incident found only after two 10-minute waits.
* An import that is pending but does not run because it failed (e.g. a `Malformed theory`, a failed `ML_file`; its status stays at 99%) is no longer described as "still being processed" with the advice to repeat: `get_state` and `edit` (`check`) say `*** BLOCKED, NOT RUNNING: X waits for its import Y, which has failed at line N and is not running: <first error>. Waiting or repeating this call changes nothing: fix Y first ***`, the wait ends after 3 seconds instead of using up `wait_seconds` (one incident burned two 10-minute waits), and the progress line says the same instead of `(99%)`.
* Wait progress for the human watching: every 10 seconds, the wait loops of `get_state`, `edit` (`check`) and file loading, and a running `start_session`, send a short line as MCP progress notification (shown by terminal clients; the VS Code panel shows none) and append it to `<server cwd>/.pide_mcp/status.log` (the directory ignores itself in git): `waiting: Box_Tests.thy: 61 of 92 commands, running line 143, 40 s`, or `... BLOCKED, nothing runs: failure at line 1: ...`, or `... waits for imports X (61%)`. A wait for a file that is blocked (nothing runs, commands unprocessed after a failure, no import pending) now ends after 3 seconds instead of using up `wait_seconds`. `.claude/hooks/wait_notice.py` (PreToolUse/PostToolUse) shows the human when a call waits and how long it took; see README.md.
* `get_state` and `edit` (`check`): when nothing in the file is running and commands stay unprocessed because an earlier command (usually the header, e.g. `Bad theory name` or `Bad theory import`) failed, the result says `*** BLOCKED, NOT RUNNING ... ***` with that failure's message in full, instead of `PROVISIONAL ... repeat with wait_seconds`, which sent agents polling for something that never happened. `PROVISIONAL` stays for files that are really running or waiting for imports. A `get_state` result that is identical for the third time in a row ends with a note that waiting or repeating changes nothing.
* `create_scratch` with `content` says in its result when the `theory` name in the content does not match the file name (or no header is there).
* `start_session` with a bare session name that the server was configured with (`-S`, e.g. `session: "BoxDev"`) reuses that configuration and says so; a bare name that was not configured starts a plain session and says that (before it silently started a plain HOL session, whose theories are then named by file path). Passing arguments for a configured name overrides the configuration, with a note.
* `get_state`: new `max_output_lines` (default 400): a hard cap on the text result, with a note about what was cut. A theory whose header failed on an import is unloaded and loaded again by `get_state`, so that an import that exists now is found (before it stayed failed until the file was touched). The "external edits synced" note points to `edit` with `check`.
* `edit` with `check` also reports `edited_range`: the problems and warnings of the edited commands themselves (a goal-stating command that is merely open with a warning no longer hides behind a `first_problem` that points at the following `end`) and how many of them print writeln/information output; it also carries the import and Interrupt hints. The description asks for edits to one file one after the other.
* The earlier-problems banner counts only failed or sorry'd commands (a plain warning was counted before). First messages in the locations view and the check summary are cut at 300 characters (before: 200) at a word boundary.
* `create_scratch` has a `content` argument (the complete initial file text; `imports` is then ignored). Every tool result now notes arguments that are not in the tool's schema (`note: ignored unknown argument(s): ...`; before they were ignored silently, e.g. a `content` that did not exist). `unload` accepts `origin` as well as `origins`.
* Skills: the global copies of the skills (`~/.claude/skills` etc.) are plain copies and go stale after every skill commit of this repository; agents started outside the repository follow the old text. README.md says so: run `dev/sync_skills.sh` (it re-installs the Claude Code copies and keeps a backup) after every commit that changes the skills. The skill changes of this series (`&&&` goals, basic idioms and traps, `try0` only when the reason is unknown, eta and nested datatypes, session-qualified imports) reached only agents running inside this repository until the global copies are updated.
* `edit` with `check` waits up to `check_wait_seconds` (default 30) for the file and its imports to settle before it takes the status, so the result is usually final (before: it nearly always said PROVISIONAL and needed a `get_state` with `wait_settled`).
* `include_infos` collapses three or more `consts` messages of one command (the generated constants of a `datatype`) into one line. The failure hint now distinguishes `Failed to apply proof method` (goal before the method) from `Failed to finish proof` (the state where the proof got stuck). The earlier-problems banner counts distinct problem commands; `reprocessed` counts only proper commands (not whitespace and comment spans). `unload` says when nothing was loaded under the given origins.
* `get_state`: when the requested range starts after failed or sorry'd commands, a banner `*** earlier problems: N failed or sorry'd commands before line L (first at line X): later commands may rest on them ... ***` says so (a failed lemma stays usable by later commands, which then show `finished`); the failure hint says the same. After an external edit was synchronised, the note also tells how many theories and commands it reprocesses (counts only: the previous processing time is gone then).
* Integer and boolean arguments are also accepted as strings (`"600"`, `"true"`): clients that still use an outdated copy of a tool's schema (after a server restart) send newly added parameters as strings and got `Malformed ...`.
* The failure hint of `get_state` says that the goal in the error of a failed method is the state before that method, and points to the "Basic idioms and traps" section of the `isabelle-proof-development` skill. A long `get_state` text (over 150 lines) ends with a hint to use `detail: summary`/`locations` or a narrower line range.
* Memory: `stop_session` runs a garbage collection. ZGC hands unused heap back to the OS only after 300 s by default, so an idle server kept 3.7 GB after its sessions had stopped; `dev/mcp_reload_proxy.py` therefore starts the server with the environment variable `PIDE_MCP_JVM_OPTIONS=-XX:ZUncommitDelay=30` (`--java-options` changes it), which `etc/settings` appends to `ISABELLE_TOOL_JAVA_OPTIONS`: only processes that set the variable are affected, other Isabelle JVMs (jEdit, VS Code, batch builds) are not. Without the proxy, set `PIDE_MCP_JVM_OPTIONS` in the MCP server entry (Isabelle's launcher drops `JAVA_TOOL_OPTIONS`). The `machine` block notes that other Isabelle instances (e.g. the VS Code Isabelle extension) count against the machine's memory.
* `dev/mcp_reload_proxy.py` reaps a server that died on its own and logs it.
* `get_state`: `wait_settled` no longer returns early because the file already has a failed command (it waited only while nothing had failed); it waits until the file and its imports are settled. New `stop_at_error` stops the wait when one more command fails. `wait_settled` without `wait_seconds` waits up to 60 seconds (before: it did nothing). With `include_infos` but not `detail: full`, a note says why no infos are shown. The failure hint says that commands after a failed command of the same proof run on the state before it.
* `find_theorems`, `find_consts`, `suggest_facts`: a file that is not loaded yet is loaded and waited for (up to 30 seconds) instead of failing the first query. The hint about non-imported theories also shows for `found nothing`.
* `edit`: with `check`, the `provisional` entry comes first; the tool description states that untouched lines are preserved byte for byte.
* New development helper `dev/mcp_reload_proxy.py`: a stdio proxy in front of `isabelle pide_mcp` that restarts the server on the next request after its sources changed (no manual MCP reconnect). Its first version leaked memory: stopping the old server sent SIGTERM to the bash wrapper only, so the old java and its `poly` processes (several GB with a large session) kept running, reparented to init, for as long as the proxy lived; repeated restarts ran a machine out of memory. Fixed: the proxy now closes the old server's stdin (the Java server then shuts down and stops its Isabelle processes) and escalates to SIGTERM/SIGKILL of the whole process tree after a timeout. Proxies started before the fix keep the old behaviour until they are restarted, i.e. until the MCP is reconnected once.
* Out-of-range integer arguments are reported with the allowed range (before: just `Malformed ...`).
* `create_scratch`: the extension defaults to `.thy` and a missing leading dot is added (before, `create_scratch` without extension created an unloadable file). The result includes the `theory` name for the header. New argument `imports` initialises a new `.thy` file with a theory skeleton. Files without any extension now give a clear error instead of `Illegal character "/" in path element`.
* `get_state`: `commands_limit` 0 no longer implies `detail: summary`. The default `detail` is `full` for a positive `commands_limit` and `locations` otherwise, so that `commands_limit: 0` still lists the problems. New argument `include_ml_echo` (default true; with `include_infos`) to drop the echo of top-level ML declarations. INCOMPATIBILITY.
* `get_state` no longer lists whitespace and comment-only spans as commands (they appeared as blank entries with misleading line numbers and inflated the command counts).
* `get_state` with `wait_seconds` also waits while the file only waits for imported theories that are still being processed (e.g. after editing an imported file), instead of returning all commands as unprocessed. The result lists such theories as `waiting_for` (with progress), also without `wait_seconds`.
* `get_state` marks first messages that leave out further lines (`(+N more lines, see detail: full)`). New argument `info_max_lines` (default 30) caps each writeln/information/tracing message shown with `include_infos`, e.g. the echo of long ML bindings.
* `get_state` on a line range now reports the status, messages, `bad` markers and source of every command overlapping the range in full, instead of cutting them to the range: a failed multi-line command no longer shows up without its error message. Types, facts, and markup still respect the range. The first message in `summary` and `locations` skips header-only lines such as `ML error:`. For `.ML` files (a single command), errors outside the requested lines are reported as problem kind `errors_outside_range` with a hint instead of showing no problem.
* Synchronised external edits are also written as a unified diff to a file in directory `pide_mcp_sync_diff_dir` (default `.pide_mcp/sync_diffs`, relative to the server's working directory, i.e. the project; the directory ignores itself in git; set empty to disable); only the file name is reported to the agent, so that the diff can be reviewed without using up its context. The newest 100 diffs are kept.
* All tools now return readable text (real line breaks, no JSON quoting) as content only, without `structuredContent`. `find_entities` gets the `format` argument of `get_state` (`format: json` for the previous output). INCOMPATIBILITY.
* `get_state`, `get_session_state`, and `find_entities` now synchronise loaded files that were edited on disk outside of the server (e.g. by scripts or `sed`) before answering, so an explicit `read` is no longer needed. Only the changed line spans are sent to PIDE. The result reports them as `external_edits_synced`.
* `get_state` and `get_session_state` now return readable text (real line breaks, no JSON quoting) as content only, without `structuredContent`. Pass `format: json` for the previous JSON output including `structuredContent`. INCOMPATIBILITY.
* `get_session_state` has a new argument `include_failures`: first failing command and failing lines per theory.
* `get_state` has a new argument `wait_seconds` to wait for files that are not loaded or processed yet.
* `get_state` output is now compact. New arguments `detail` (`summary`, `locations`, `full`), `problems_limit`, and `source_max_lines`. Problematic commands are listed once in `problems` (with their `kinds`) instead of once per kind, and `first_problem` reports the first failing command. Command sources are truncated. The `commands_*` detail lists and `errors`/`warnings` detail lists are replaced by counts. INCOMPATIBILITY.
* Reading or editing a theory loads its unloaded files.
* `unload` now also unloads files of unloaded theories unless a remaining theory still loads them.
* Add [tool\_extensions](./tool_extensions) with experimental sledgehammer tool as an example user-level tool extension.
* Add overlay and query operations support.
* Remove `show_results` default value. Set options manually if required. INCOMPATIBILITY.
* Enable `show_states` only for live sessions, not for base session builds. Disable `editor_output_state` to avoid duplicate states. INCOMPATIBILITY.
* More robust session start and stop. Introduce new phase `building`. `stop_session` can now also stop sessions that are not running.
* Failing tool calls now return a result with `isError` instead of a JSON-RPC error. INCOMPATIBILITY.
* Tool results are now also returned as `structuredContent`.
* New options `pide_mcp_await_option_sessions` and `pide_mcp_exit_on_failed_option_sessions` control whether sessions given as command-line options are prepared before the MCP server starts
    and whether the MCP server stops if one such sessions fails to start.
* Command-line option `-L` now logs to the file in addition to the console. INCOMPATIBILITY.
* New command-line option `-w` logs MCP requests and responses while `-v` no longer does. INCOMPATIBILITY.
* Support of `notifications/cancelled` for long-running tool calls.
* Long-running operations now report progress, configurable with options `pide_mcp_session_progress_delay` 
    and `pide_mcp_progress_threshold`.
* New option `pide_mcp_tools` to enable/disable tools at startup time.
* New tool `get_session_state` shows session information, status, progress, and resource statistics, superseding tools `list_loaded_theories` and `list_session_directories`. INCOMPATIBILITY.
    Runtime statistics are reported as averages and maxima over a sampling window,
    configurable via option `pide_mcp_session_statistics_limit`.
* New command-line option `-S` starts further sessions on startup.
    Isabelle system options given outside `-S` are inherited by the sessions given via `-S`.
    An invocation with only Isabelle system options does not start a session.
    Use `-S ""` to force a session start in such cases. INCOMPATIBILITY.
* Support for multi session handling and new tools `start_session`, `stop_session`, and `list_sessions`.
    Existing tools now take an optional session id, which may be omitted when exactly one session runs.
    `PIDE_MCP_Tool`s now receive several sessions. INCOMPATIBILITY.
* Update `get_state`: include tracing, remove unprocessed command details, and fix wrong message line number attribution for blobs.
* Set visible perspective on last read or edited origin only. Dependencies are hidden. Use option `pide_mcp_range_context` to adjust number of lines around range that stay visible.
* Await stable snapshot after editing operations (without blocking other tools)
* Reworked loading and editing: closes several issues reported by Diego Marmsoler and Yong Kiam Tan (stuck process due to invalid imports and de-synchronisation of session and resources, edit race conditions, etc.)
* New tool `unload`: Remove ("clean") a theory and its dependents.
* Add tool plugin system: users can freely add and remove (new) tools.
* The `edit` tool now matches substrings within a given range and can edit multiple occurrences at once.
    This is in line with how most coding agents implement their edit tools.
